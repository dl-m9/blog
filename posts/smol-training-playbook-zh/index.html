      引言

      今天，训练一个高性能的大语言模型究竟需要什么？

      阅读时间：2 到 4 天

      已发表的研究把这件事写得很直白：选好架构，精心整理数据，算力给够，结果自然漂亮。论文里的结果光鲜，消融实验条理清晰，事后回看，每个决策都显得理所当然。但这些报告只呈现了奏效的部分，还带上一层美化的滤镜。它们不会写凌晨两点还在调试数据加载器的时刻，不会写突然飙升的损失曲线，也不会写某个隐蔽的张量并行 bug 如何悄悄拖垮整次训练（后文会讲到）。真实情况要混乱得多，充满反复试错，以及大量最终没有写进论文的决策。

      接下来，我们要带你走到 SmolLM3 训练的幕后。这是一个在 11T tokens 上训练出来的 30 亿参数多语言推理模型。这不是一份普通指南，而是把一张由决策、发现和死胡同织成的蛛网逐一拆开，从中提炼出「造出世界级语言模型到底靠什么」的洞察。

      它也是我们长篇模型训练系列的收官之作。此前我们讲过如何构建大规模数据集（FineWeb）、如何让数千张 GPU 协同工作（The Ultra-Scale Playbook）、以及如何在每个环节选对评估（The LLM Evaluation Guidebook）。现在我们把这些拼起来，真正训出一个强模型。你会看到完整过程，不只是最后奏效的配方，还有那些塑造了每个决策的失败、基础设施故障和调试过程。你会看到小规模消融里很有希望的结果为何无法迁移到大规模，我们为什么在训练到 1T tokens 后重启了一次，我们如何在多语言、数学和代码之间权衡，同时保持强劲的英文表现，以及最后如何做出一个混合推理模型。

      我们不想简单罗列做过的每件事，而是把这段经历讲成一个有组织的故事。如果你正从「我们有很好的数据和 GPU」走向「我们训出了一个很强的模型」，这份指南就是写给你的。希望这样的坦诚能缩小研究与生产之间的鸿沟，让你的下一次训练少一点混乱。

      如何阅读本指南

      你不必从头读到尾，而且以它现在的篇幅，一口气读完本来也不现实。全书分成几个相对独立的部分，任意一部分都可以跳过或单独阅读：

      • 训练指南针：从高层讨论你是否应该自己预训练一个模型。在烧掉投资人的钱之前，我们会带你过一遍必须自问的根本问题，并给出系统化的决策思路。这部分偏战略，想直接看技术内容可以放心跳过。
      • 预训练：训练指南针之后的部分覆盖构建一份可靠预训练配方所需的全部内容：如何做消融、如何选评估、如何混合数据源、如何做架构选择、如何调超参数，以及如何熬过训练马拉松。即使你不打算从零预训练，只要关心持续预训练（也叫中期训练），这部分同样有用。
      • 后训练：这一部分讲如何让预训练模型发挥全部潜力。我们会走完整个后训练字母表，从 SFT、DPO 到 GRPO，以及模型合并这类带点玄学的手艺。让这些算法真正起作用的经验，大多是踩坑换来的，我们希望写下来能替你省掉一些。
      • 基础设施：如果预训练是蛋糕，后训练是糖霜和樱桃，那基础设施就是工业级烤箱。没有它什么都做不出来，它一坏，你周日下午愉快的烘焙就变成火灾隐患。如何理解、分析和调试 GPU 集群的知识，零散分布在各种库、文档和论坛里。这一部分讲 GPU 布局、CPU 与 GPU、节点与存储之间的通信模式，以及如何定位并消除瓶颈。

      训练指南针：为什么 → 做什么 → 怎么做

      机器学习领域对「优化」有一种近乎执念的迷恋。我们盯着损失曲线、模型架构和吞吐量，毕竟机器学习的本质就是优化模型的损失函数。但在扎进这些技术细节之前，有一个更根本的问题常常没人问：我们到底该不该训这个模型？

      看看后面的模型发布热力图就知道，开源 AI 生态几乎每天都在放出世界级模型：Qwen、Gemma、DeepSeek、Kimi、Llama 🪦、OLMo，这份名单每个月都在变长。它们不是研究原型或玩具示例，而是覆盖多语言理解、代码生成、推理等广泛场景的生产级模型，多数还带着宽松许可证和活跃的社区支持。

      于是有了一个让人不太舒服的结论：也许你并不需要训练自己的模型。

      用这句话给一份「LLM 训练指南」开篇看着有点怪。但很多失败的训练项目并不是败在超参数或代码 bug 上，而是败在有人决定去训一个根本不需要的模型。所以在投入训练、研究怎么做之前，你得先回答两个问题：为什么要训这个模型？该训什么样的模型？没有清晰答案，你可能浪费几个月算力和工程时间，造出一个世界上已经有了的东西，甚至是一个没人需要的东西。

      先从为什么开始。不明确目的，后面任何决策都无法自洽。

      📍 关于这一节。这一节和全书其余部分不太一样，重点不在实验和技术细节，而在战略规划。我们会带你判断是否需要从零训练，以及要造一个什么模型。如果你已经把「为什么」和「做什么」想清楚了，可以直接跳到原文「Every Big Model Starts with a Small Ablation」看技术细节。如果还不确定，在这里多花点时间很可能在后面省下大量力气。

      为什么：那个没人愿意回答的问题

      直说实际会发生什么。某人（运气不错）拿到了一个 GPU 集群，可能来自科研经费，也可能是公司闲置算力，然后思路大致是这样的：「我们有 100 张 H100，能用三个月，训个模型吧！」模型规模随手一拍，数据集把手头能找到的凑一凑，训练就这么开始了。六个月后，算力预算和团队士气都烧得差不多了，训出来的模型没人用，因为从头到尾没人问过为什么。

      以下是若干「不该训模型」的理由。被「我们训出了自己的模型」这句话吸引很正常，但在投入大量时间和资源之前，值得先问一句：我们为什么需要训这个模型？

      下面这张决策流程图梳理了启动大型预训练项目前应该走一遍的思考过程。从技术角度看，你首先应该确认的是：有没有一个现成模型，靠提示词或者微调就能把活干了。

      顺带说明：这里讨论的「为什么」特指从零训练。本指南不讲蒸馏和剪枝，它们同样是造出高效模型的有效路径，但工作流与从零训练不同。想概览这些主题，推荐 NVIDIA 的 Minitron 论文。

      定制预训练真正说得通的场景基本只有三类：你想做新颖的研究、你的生产场景有非常特殊的需求、或者你想填补开源模型生态里的一块空白。下面分别看。

      研究：你到底想弄明白什么？

      LLM 领域可做的研究很多，共同点是通常从一个定义清晰的问题出发：

      • 能不能把这个新优化器的训练扩展到 10B 以上规模的模型？（见 Muon is Scalable for LLM Training）
      • 只用强化学习、不用监督微调（SFT），能不能产生推理能力？（见 DeepSeek-R1）
      • 只用合成的教科书数据，能不能训出好的小模型？（见 Textbooks Are All You Need）
      • 只用开放许可的数据训练，能不能达到有竞争力的表现？（见 The Common Pile v0.1）

      把假设写得越具体越好，同时想清楚实验所需的规模，成功的概率会明显提高。

      生产：为什么不能用现成模型？

      公司无法直接拿现成模型来用，主要有三类原因，两类是技术性的，一类来自治理要求。

      第一个理由是领域特殊性：你的数据或任务涉及高度专业的词汇或结构，现有模型处理不好。比如你可能想训：

      • 一个词表独特、且有长程依赖的 DNA 模型
      • 一个需要深度熟悉领域术语与逻辑的法律或金融模型

      第二个与之相关，是部署约束：你需要一个贴合自家硬件、延迟或隐私要求的模型。例如跑在无人机上的 LLM，或者部署在 FPGA 等定制硬件上的本地系统。

      有个简单的检验方法：花几天时间，基于 Qwen3、Gemma 3 或其他当前 SOTA 模型做一版，看看靠提示词、工具调用或后训练能不能达到性能目标。如果不行，大概就该自己训了。

      即便满足需求所需的后训练预算很大，它仍可能比从零开始便宜。用 1T tokens 微调自己的模型，比从零训 10T+ tokens 经济得多。写到这里，做 LLM 训练的人会神奇地开始把它叫「中期训练」，而不是「后训练」。

      第三个理由是安全与治理：你身处受监管行业或高风险应用，需要对训练数据、模型行为和更新周期有完全控制，必须确切知道模型里进了什么，并且能向监管方证明。某些情况下，除了自研别无选择。

      这些是公司自研模型的主要原因。那么发布开源模型的公司或组织又是为什么？

      战略开源：你看到了一块能补上的空白吗？

      经验丰富的 AI 实验室发布新开源模型，最常见的原因之一，是他们在开源生态里识别出了一块具体空白，或一个新的 AI 使用场景。

      套路通常是这样：你注意到一个尚未被充分探索的方向，比如没有长上下文很强的端侧模型，或者多语言模型虽然有了，但在低资源语言上很弱，又或者领域正在转向 Genie 3 那样的交互式世界模型，而市面上没有好的开放权重模型。

      你有理由相信自己能做得更好，也许是因为整理出了更好的训练数据、打磨出了更好的训练配方，或者有算力支撑别人做不到的过度训练。你的目标很具体，不是「史上最好的模型」，而是「端侧最好用的 3B 模型」或者「第一个支持 1M token 上下文的小模型」。

      这是个实在的目标，成了就有价值：开发者采用你的模型，它变成别人的基础设施，或者为你建立技术信誉。但成功需要经验，你得知道什么真的可行，以及在一个竞争激烈的领域里如何稳定交付。为了讲具体些，看看 Hugging Face 自己怎么想这个问题。

      Hugging Face 走过的路

      Hugging Face 为什么要训开放模型？答案很简单：我们做对开源生态有用的东西，补上很少有人补的空白。

      虽然开放权重模型有数百万个，但训练「完全开放」模型的组织非常少。除了 Hugging Face，还有 Ai2 和 斯坦福的 Marin 社区。

      这里既包括数据集、工具链，也包括训练模型本身。我们启动的每一个 LLM 训练项目，都始于「注意到一块空白，并相信我们能在其中做出有意义的贡献」。

      第一个 LLM 项目始于 GPT-3 发布之后。当时感觉没有别人在做开放替代方案，我们担心这些知识最终被锁在少数几家工业实验室里，于是发起 BigScience workshop，训练开放版本的 GPT-3。成果是 BLOOM，由数十位贡献者用一年时间搭建训练栈、分词器和预训练语料，最终预训练出一个 175B 参数模型。

      BLOOM 的继任者是 2022 年的 StarCoder。OpenAI 为 GitHub Copilot 开发了 Codex，但它是闭源的，做一个开源替代显然对生态有价值。于是我们在 BigCode 框架下与 ServiceNow 合作，构建了 The Stack 数据集，并训练 StarCoder 15B 来复现 Codex。StarCoder2 则来自两条经验：我们本可以训得更久，以及「小模型训更久」可能比「一个大模型」更有价值。我们训了一个 3B / 7B / 15B 的系列，每个都用数万亿 tokens，远超当时开放代码模型的做法。

      SmolLM 系列沿用了同样的思路。我们注意到强的小型模型非常少，而当时刚做完 FineWeb-Edu 这个很强的预训练数据集。SmolLM（135M / 360M / 1.7B）是第一版，SmolLM2 聚焦更好的数据和更长的训练，在多个维度达到 SOTA，SmolLM3 则扩展到 3B 参数，同时加入混合推理、多语言和长上下文这些社区在意的特性。

      这个模式也延伸到预训练之外：我们训练 Zephyr 来证明 DPO 在大规模上可行，发起 Open-R1 复现 DeepSeek-R1 的蒸馏流程，发布面向竞赛编程的 OlympicCoder，在国际信息学奥赛题目上达到 SOTA。我们还用 SmolVLM 探索视觉、用 SmolVLA 探索机器人等其他模态。想了解 Hugging Face 的科学项目全貌，可以看 huggingface.co/science。

      希望这一节已经说服你：认真想清楚「为什么要训模型」是有价值的。本指南余下部分，我们默认你已经做完这番自省，并且有一个站得住脚的理由。

      做什么：把目标翻译成决策

      知道了为什么训，接下来该训什么？这里的「什么」指模型类型（稠密、混合专家、混合架构，或者全新的东西）、模型规模、架构细节和数据配比。一旦把「为什么」定下来，「做什么」就可以从中推出来。比如：

      • 端侧要快 → 小而高效的模型
      • 多语言模型 → 更大的分词器词表
      • 超长上下文 → 混合架构

      除了由使用场景驱动的决策，还有一些选择是为了优化训练本身：更稳定、样本效率更高，或者更快。这些决策不一定那么非黑即白，但可以把决策过程大致拆成两个阶段：

      • 规划：跑实验之前，把使用场景映射到需要拍板的各个组件上。部署环境决定模型规模约束，时间线决定你能承担哪些架构风险，目标能力决定数据集要求。这个阶段要做的是，把「为什么」里的每条约束，连接到「做什么」里的具体规格。
      • 验证：有了起点和一份候选改动清单之后，系统地做测试。测试很贵，所以聚焦在那些可能切实改善你的场景表现、或优化训练本身的改动上。这就是「Every Big Model Starts with a Small Ablation」里讲的消融实验。

      📍 学会判断什么值得测，而不只是会跑测试。在无关选择上做完美消融，浪费的算力和在重要选择上做粗糙消融一样多。

      后面的章节会讲到定义模型时可选的所有方案，以及如何用系统性实验把范围收窄。在此之前，我们先分享几条关于团队与项目组织的经验，来自我们自己训模型，以及观察其他优秀团队打造强 LLM 的过程。

      超能力：迭代速度与数据

      条条大路通罗马，但我们发现，真正把成功的 LLM 训练团队区分出来的是迭代速度。训 LLM 本质上是一门边做边学的手艺：训得越频繁，团队进步越快。所以，一年训一个模型的团队和一季度训一个的团队相比，后者成长会快得多。看看 Qwen 和 DeepSeek 的团队就明白了，如今家喻户晓的它们，长期保持稳定且高频的模型发布节奏。

      除迭代速度之外，对 LLM 训练影响最大的因素是数据整理。人天然倾向于一头扎进架构选择里改进模型，但真正擅长的团队，对高质量数据的执念超过其他一切。

      还有一个与迭代速度相关的因素是团队规模。就主要的预训练任务而言，只需要少数几个人配上足够算力就能执行。今天要预训练一个 Llama 3 量级的模型，大概两三个人就够。等到涉足更多样的训练和下游任务（多模态、多语言、后训练等），才需要为每个领域补充几位专精的人。

      所以，从一个小而装备精良的团队起步，每两三个月训一个新模型，用不了多久你就能爬到顶部。本指南剩下的部分，就聚焦这个团队日常的技术工作。

      每个大模型都始于一次小规模消融

      在真正开始训练 LLM 之前，我们要做很多决定，它们会塑造模型的表现和训练效率。哪种架构最适合自己的场景？该用什么优化器和学习率调度？数据源又要怎么混？

      「这些决定是怎么做出来的」是个高频问题。有人以为靠深思熟虑就够了。战略思考当然必不可少（上一节讲过），但光靠推理并不够。LLM 并不总是符合直觉，关于「什么应该奏效」的假设，实践里常常落空。

      比如，用看起来「质量最高的数据」不一定训出更强的模型。以 arXiv 为例，它汇集了人类海量的科学知识。直觉上，拿这么丰富的 STEM 数据训练，模型应该更强，对吧？实际上并不会，对小模型甚至可能伤害表现。原因在哪？arXiv 论文确实充满知识，但高度专业化，写作是狭窄的学术文体，和模型最擅长学习的多样、通用文本差别很大。

      那么，盯着问题苦想没有用，怎么知道什么有效？像合格的经验主义者那样，做大量实验。机器学习不是纯数学，它其实非常是一门实验科学。

      在很多方面，机器学习像统计力学被发现之前的热力学：我们有可靠的经验规律和设计原则，效果出奇地好，尽管更深层的理论解释仍在形成中。

      这些实验会指导许多关键决策，因此把它们搭好非常重要。我们主要想要两个属性：

      1. 快：跑得尽可能快，才能频繁迭代。消融做得越多，能检验的假设越多。
      2. 可靠：要有强区分能力。如果所看的指标在早期无法有效区分不同配置，消融可能什么也揭示不了。要是噪声还大，我们甚至会追着噪声跑。更多细节见我们把 FineWeb 扩展到 1000 多种语言的博客文章。

      不过在搭建消融之前，还得先对架构类型和模型规模做几个基础选择。这些由指南针引导的决定，会影响用哪个训练框架、算力预算怎么分配，以及从哪个基线起步。

      SmolLM3 选的是 3B 参数的稠密 Llama 式架构，因为目标是端侧小模型。但正如后文「设计模型架构」会讲到的，混合专家（MoE）或混合架构也许更适合你的场景，不同模型规模也各有取舍。后面会深入探讨这些选择，并展示如何做决定。现在先从最实际的第一步开始：选基线。

      选择你的基线

      每个成功的模型都建立在一个经过验证的地基上，再按自身需求改造。Qwen 训练第一代模型族时从 Llama 架构起步，Meta 训练 Llama 3 时从 Llama 2 起步，Kimi K2 从 DeepSeek-V3 的 MoE 架构起步。这不只是架构，训练超参数和优化器也一样。

      为什么？设计好的架构和训练配置，需要许多组织花数年迭代。标准 transformer 和 Adam 这类优化器，是数千次实验打磨出来的，人们已经找出了失效模式、调试过不稳定、优化过实现。从验证过的地基出发，等于继承所有这些积累。从零开始，意味着每个坑都要自己重新踩一遍。

      一个好的起点架构应该：

      • 匹配你的约束，与部署目标和使用场景一致
      • 在目标规模上被验证过，在同等或更大规模的万亿 token 级训练中跑通过
      • 文档完善，有在开放模型上验证过可用的已知超参数
      • 框架支持良好，最好同时被你考虑的训练框架和计划使用的推理框架支持

      修改基线：去风险的纪律

      现在你有了一个能跑、且贴合场景的基线。到此为止也行，直接拿去训，只要数据配比不错，大概率能得到一个像样的模型，很多成功项目就是这么做的。但基线不是为你的特定约束优化的，它是为构建者的场景和部署目标设计的。所以多半存在一些值得做的改动，让它更贴合你的目标。然而每次架构改动都带风险：可能提升表现，可能拖垮，也可能什么都没做却白白烧掉消融算力。

      让你不跑偏的纪律叫去风险：除非测过确实有帮助，否则不改任何东西。

      📍 什么算「已去风险」？当测试表明某项改动要么提升了目标能力上的表现，要么带来了实质收益（推理更快、显存更省、稳定性更好），且没有把表现拖到你可接受范围之外，就算完成去风险。

      棘手的地方在于，基线和训练配置里能改的组件很多：注意力机制、位置编码、激活函数、优化器、训练超参数、归一化方案、模型布局等等。每一个都是一个潜在实验，而这些组件之间常常以非线性方式相互作用。你既没有时间也没有算力去测遍一切，或穷尽所有交互。

      所以，先拿有希望的改动对着当前基线测。有效就把它合入、形成新基线，再对着新基线测下一个改动。算力允许的话，也可以逐项单独测试并做留一法分析。别掉进对每个超参数做穷举网格搜索、或者把新出的架构变体全都试一遍的陷阱。这套方法的实例可以看 ScaleRL 论文。

      🎯 有策略地做实验。会跑实验不够，还得知道哪些实验值得跑。测任何改动前先问两句：它对我的具体场景有帮助吗？它能优化我的训练吗？两个问题都不沾边的，跳过。

      现在你已经知道如何通过战略规划识别值得试的方向，接下来进入实证验证。后几节会讲怎么实际检验这些改动，包括如何搭可靠的实验、如何解读结果、如何避开常见陷阱。再往后的章节，会用具体例子走一遍架构、数据、基础设施和训练决策的测试过程。

      挑选训练框架

      要做的第一个决定，是用哪个框架训练模型，以及顺带用它跑完所有消融。

      别逞英雄，在消融和最终训练之间换框架，那条路通向痛苦。

      这个选择要平衡三点：

      1. 框架必须支持目标架构，或者能让我们轻松扩展它。
      2. 它要稳定、生产可用，不能训练到一半莫名其妙崩掉。
      3. 吞吐量要强，才能快速迭代、把算力预算用足。

      实践里这些要求可能互相拉扯，形成取舍。看看可选方案：

      框架特性实战验证优化程度代码行数（核心 / 总计）扩展性与调试
      Megatron-LM✅ 丰富✅ Kimi K2、Nemotron✅ 3D 并行的开创者93k / 269k⚠️ 新手较难
      DeepSpeed✅ 丰富✅ BLOOM、GLM✅ ZeRO 与 3D 并行的开创者94k / 194k⚠️ 新手较难
      TorchTitan⚡ 特性仍在增长⚠️ 较新，但由 PyTorch 团队验证⚡ 针对稠密模型优化，MoE 改进进行中7k / 9k⚡ 中等，需要并行知识

      这张表概括了主流框架的关键取舍。前三个框架的代码行数来自 TorchTitan 技术报告。逐个展开说：

      • NVIDIA 的 Megatron-LM 已经存在多年，久经实战。Kimi 的 K2 就是靠它训出来的，吞吐量扎实，生产所需的大部分特性都具备。但成熟带来复杂度：代码库对新手来说不好读、也不好改。
      • DeepSpeed 属于同一类。它是 ZeRO 优化的开创者，支撑过 BLOOM 和 GLM。和 Megatron-LM 一样久经实战且深度优化，也同样复杂。19.4 万行的总代码量在起步时颇有压迫感，尤其要实现自定义特性或调试意外行为的时候。
      • 另一边，PyTorch 新近的 TorchTitan 轻得多，代码库紧凑且模块化，读起来简单。它具备预训练所需的核心特性，很适合快速实验。不过因为较新，实战检验没那么充分，活跃开发中也仍可能有点不稳定。
      • Nanotron 是我们从零搭的框架，这带来了完全的灵活性和对大规模预训练的深入理解，这些洞察后来长成了 Ultra-Scale Playbook。开源之后我们也收到了社区有价值的反馈，但多数情况下还是得自己先把特性跑通验证。它现在支持训练所需的全部生产特性，MoE 支持等领域仍在补齐。

      从零自研对我们是合理的，但它要求团队在专业能力和时间上重投入，用来调试问题和补齐缺失特性。一个很好的替代方案是 fork 现有框架再按需求增强，比如 Thinking Machines Lab 的内部预训练库就是 TorchTitan 的一个 fork。

      最终选哪个，取决于团队专长、目标特性，以及你愿意在自研上投多少时间，还是直接用最生产就绪的方案。如果多个框架都满足需求，就在自己的硬件上比一比吞吐量。做快速实验和跑速度测试时，代码库更简单的往往胜出。

      搭建消融实验

      框架定了，接着设计消融配置。实验要快到能迅速迭代，又要大到结果有信号、能迁移到最终模型。

      建立消融框架

      消融的目标是在小规模上跑实验，拿到能放心外推到最终生产训练的结果。

      主要有两种做法。一是保持目标模型规模，少训一些 tokens。SmolLM3 的消融训的是完整 3B 模型，但只用了 100B tokens，而不是最终的 11T。二是目标模型太大时，训一个更小的代理模型。比如 Kimi 研发 1T 参数、32B 激活参数的 K2 时，所有消融都用全尺寸会贵到无法承受，于是部分消融放在 3B MoE、0.5B 激活参数上做。

      一个关键问题是：小规模上的结论真的能迁移吗？我们的经验是，如果某改动在小规模上伤害表现，可以放心地在大规模上排除它。但如果它在小规模上有效，你得确认已经训了足够多的 tokens，才能以较高把握断定结论能外推到更大尺度。训得越久、消融模型越接近最终模型越好。

      我们决定所有消融都用一个原版 vanilla transformer 作基线。主配置是遵循 Llama 3.2 1B 架构的 1B transformer，训练 45B tokens。用这份 Nanotron 配置，在 8 张 H100 的单节点上大约一天半训完（每 GPU 每秒 42k tokens）。

      我们训 45B tokens 是为了拿到稳定信号，尽管对这个规模来说约 35B 才是 Chinchilla 最优。

      ☝️ 一次只改一件事。每次消融只改一个变量，其他全部保持不变。同时改了多处而表现提升，你不会知道是哪一处起了作用。逐项测试改动，再把有效的组合起来重新评估。

      跑消融时，有些架构改动会显著改变参数量。比如从绑定词嵌入改为不绑定，嵌入参数直接翻倍。用分组查询注意力或多查询注意力替代多头注意力，注意力参数会大幅减少（这些后面都会讲）。为了公平比较，需要跟踪参数量，偶尔调整别的超参数（比如 hidden size 或层数）把模型规模拉回大致相同。下面是我们用来估算不同配置参数量的简单函数：

      from transformers import LlamaConfig, LlamaForCausalLM

def count_parameters(
    tie_embeddings=True,
    num_key_value_heads=4,
    num_attention_heads=32,
    hidden_size=2048,
    num_hidden_layers=16,
    intermediate_size=8192,
    vocab_size=128256,
    sequence_length=4096,
):
    config = LlamaConfig(
        hidden_size=hidden_size,
        num_hidden_layers=num_hidden_layers,
        num_attention_heads=num_attention_heads,
        num_key_value_heads=num_key_value_heads,
        intermediate_size=intermediate_size,
        vocab_size=vocab_size,
        max_position_embeddings=sequence_length,
        tie_word_embeddings=tie_embeddings,
    )
    model = LlamaForCausalLM(config)
    return f"{sum(p.numel() for p in model.parameters())/1e9:.2f}B"

      原文还提供了一个交互工具，用来可视化稠密 transformer 的参数分布，在做架构决策或为消融写配置时很好用。该计算器假设的是标准架构选择：门控前馈网络、标准的注意力头维度（hidden_size / num_heads）、每层两个 LayerNorm，且不计偏置项（如果存在）。

      理解什么奏效：评估

      消融跑起来之后，怎么判断什么有效、什么无效？

      训模型的人第一反应大概是看 loss，这确实重要，你希望它平滑下降、没有剧烈尖峰或不稳定。对很多架构选择来说，loss 与下游表现相关性不错，单独看它可能就够了。但只看 loss 并不总是可靠。拿数据消融举例，在 Wikipedia 上训练会比在网页上训练得到更低的 loss（下一个 token 更好预测），但这不代表模型能力更强。类似地，如果两次实验换了分词器，loss 不能直接比，因为文本切分方式变了。有些改动只影响特定能力（推理、数学），可能被平均 loss 冲淡。最后，即使预训练 loss 已经收敛，模型在下游任务上仍可能继续提升。

      要看到全貌、理解这些细微效应，需要更细粒度的评估。自然的做法是用下游评测去考知识、理解、推理，以及我们关心的其他领域。

      对消融而言，聚焦那些能给出良好早期信号、且噪声小的任务很有价值。FineTasks 和 FineWeb2 用四条原则定义可靠评测任务：

      • 单调性：训练越久，benchmark 分数应持续提升。
      • 低噪声：相同配置、不同随机种子训练，分数不应大幅波动。
      • 高于随机：很多能力在训练后期才涌现，长期只有随机水平的任务对消融没用。多选题格式的 MMLU 就是例子，后文会解释。
      • 排序一致性：若方法 A 在早期优于方法 B，随着训练继续，这个次序应保持稳定。

      任务质量还取决于任务形式（怎么向模型提问）和指标选择（怎么算答案分数）。

      三种常见形式是多选题格式（MCF）、完形填空形式（CF）和自由生成（FG）。MCF 要求模型从提示里显式给出、以 A/B/C/D 前缀标出的选项中选一个（MMLU 就是这么做的）。CF 不把选项写进提示，而是比较各选项的似然，看哪个更可能。FG 看给定提示下贪心生成的准确率。FG 需要模型具备大量潜在知识，在完整训练之前的短程预训练消融里通常太难，用处不大。因此小规模消融我们聚焦多选题形式（MCF 或 CF）。

      📍 提醒。对后训练模型，FG 会成为主要形式，因为我们评的是模型能否真的生成有用回答。相关评估放在「超越基座模型：后训练」一节。

      研究还表明模型在训练早期不擅长 MCF，因此 CF 更适合早期信号。于是小规模消融用 CF，主训练里再纳入 MCF（它在训练后期信号更好）。在 CF 这类序列似然评估里给答案打分时，我们把「正确答案经字符数归一化后对数概率最高」的题目占比作为准确率，这种归一化可以避免偏向短答案。

      MMLU 的 MCF 何时摆脱随机水平，取决于模型规模和训练数据。OLMES 论文发现 7B transformer 在 500B tokens 之后开始出现非随机表现，我们在 SmolLM2 里发现 1.7B 模型要到 6T tokens。也有工作认为这本质上取决于预训练 loss 是否达到某个阈值。

      我们的消融评测套件包含 FineWeb 消融用过的 benchmarks，但去掉了噪声太大的 SIQA，另外加入 GSM8K、HumanEval 这类数学与代码基准，以及用于长上下文消融的 RULER。这组任务覆盖世界知识、推理和常识，格式多样，见下表。为加快评测、代价是引入一些额外噪声，每个 benchmark 只取 1000 道题（GSM8K、HumanEval、RULER 除外，这三个在 3B SmolLM3 消融里全量使用，1B 实验则省略）。如前所述，所有多选题 benchmark 都用 CF 评估。多语言消融和正式训练会加入更多考察多语言能力的基准，后面细说。评测用 LightEval 跑。各基准要点如下：

      基准领域任务类型题量考察内容
      MMLU知识多选14k57 个学科的广泛学术知识
      ARC科学与推理多选7k中小学科学推理
      HellaSwag常识推理多选10k日常情境的常识推理（叙事续写）
      WinoGrande常识推理二选一1.7k需要世界知识的代词消解
      CommonSenseQA常识推理多选1.1k日常概念的常识推理
      OpenBookQA科学多选500基础科学事实与推理
      PIQA物理常识二选一1.8k日常物体的物理常识
      GSM8K数学自由生成1.3k小学数学应用题
      HumanEval代码自由生成164根据 docstring 合成 Python 函数

      原文还提供了可交互的样例浏览器，可以逐题看每个 benchmark 到底在考什么。注意 MMLU 和 ARC 用多选考事实知识，GSM8K 要算出数学题的数值答案，HumanEval 要生成完整 Python 代码。这种多样性保证了消融过程中测的是模型能力的不同侧面。

      消融该用哪种数据配比？

      对架构消融，我们用固定的高质量数据混合，让它在广泛任务上尽早给出信号：英文用 FineWeb-Edu、数学用 FineMath、代码用 Stack-Edu-Python。架构方面的结论应当能较好地外推到其他数据集和领域（包括多语言数据），所以数据混合可以保持简单。

      对数据消融则相反：固定架构，系统地改变数据配比，看不同数据源怎么影响模型表现。

      有时候评测差异很小。算力够的话，值得用不同种子重跑同一组消融，看看结果波动有多大。

      一套扎实的消融配置，价值不只是帮你造出好模型。主训练出问题时（无论准备多充分，总会出），你希望对自己做过的每个决定都有把握，并能迅速定位哪些组件没被测过。这份准备省下的是调试时间，保住的是以后的精神状态。

      估算消融成本

      消融很好，但要吃 GPU 时间，值得搞清楚这些实验的代价。下表是 SmolLM3 预训练的完整算力拆分：主训练（含偶发停机）、训练前与训练中的消融，以及一次意外扩展问题导致的重启和调试所花的算力（后文详述）。

      阶段GPU 数天数GPU 小时
      主预训练38430276,480
      消融（预训练）1921569,120
      消融（中期训练）1921046,080
      训练重启 / 调试384 / 1923 / 446,080
      合计--437,760

      我们估计评测成本略低于 1 万 GPU 小时。完整评测套件（英文、多语言、数学与代码）每 GPU 约 1.5 小时，整个 11T tokens 训练期间每 10B tokens 评一次，此外还有大量消融。长上下文评测尤其贵，一次在 8 张 GPU 上约 1 小时。

      数字揭示了一个重要事实：消融与调试合计 161,280 GPU 小时，超过主训练成本（276,480 GPU 小时）的一半。SmolLM3 研发期间我们跑了 100 多次消融，其中 20 天用于预训练消融、10 天用于中期训练消融、7 天用于从那次意外训练问题中恢复。

      这说明为什么消融成本必须计入算力预算：按「训练成本 + 消融 + 意外缓冲」来规划。如果你的目标是 SOTA 表现、要实现新的架构改动、或者手上还没有验证过的配方，消融就会成为一笔可观的开销，而不是几个小实验。

      DeepSeek-V3 发布时，外界盯着它 560 万美元的训练成本数字不放（见 Forbes 报道），很多人把这个数字当成全部研发开销。实际上它只反映最后一次训练运行，更大且通常看不见的支出在研究本身：导向最终配方的消融、失败运行和调试。以该模型的规模和新颖性，研究成本必然更高。

      实验守则

      一句话：多疑一点。

      • 验证评测套件。训练任何模型之前，先确认你的评测套件能复现将要对比的模型的公开结果。若有生成式基准（如 GSM8K），更要多疑，手动抽查几条样本，确认提示格式正确、后处理提取的信息无误。评测会指导每一个决定，这一步做对是项目成败的关键。
      • 任何改动都要测，再小也一样。别低估一次看起来无害的库升级，或者「只改了两行」的提交。这类小改动可能引入微妙的 bug 或性能漂移，污染你的结果。你需要在自己关心的场景上有强测试套件的库，用来防回归。有时候升级到最新版反而能解决 bug，Elana Simon 的博客文章就是一个漂亮的侦探式调试案例。
      • 一次只改一件事。实验之间保持其余条件完全一致。有些改动会以意想不到的方式相互作用，所以先评估每个改动的单独贡献，再组合起来看整体影响。
      • 训够 tokens，评测也要够。前面提过，评测套件要有足够覆盖，训练要够久才能拿到可靠信号。这里偷工减料，结果就是噪声和错误决定。

      守这些规矩可能显得过分谨慎，但另一个选择是花好几天去调试一次神秘的性能下跌，最后发现是几天前一个不相干的依赖更新造成的。黄金原则：一旦有了好配置，任何改动都不该未经测试就上线。
